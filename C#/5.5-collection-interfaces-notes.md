# 🟦 C# 5.5 — Collection Interfaces

> **Revision status:** 🟡 In Progress — review understanding before marking complete

Collection interfaces describe the operations a collection supports without tying code to one specific implementation. They help us write flexible APIs, reduce unnecessary dependencies, and communicate what a method needs or allows.

This phase covers:

- `IEnumerable<T>`
- `ICollection<T>`
- `IList<T>`
- `IReadOnlyCollection<T>`
- `IReadOnlyList<T>`
- `IDictionary<TKey, TValue>`

The key idea is to choose the **least powerful interface that provides the operations the code actually needs**.

---

## 1. Why collection interfaces exist

Imagine a method that only needs to loop through employee records:

```csharp
public void PrintEmployees(List<Employee> employees)
{
    foreach (Employee employee in employees)
    {
        Console.WriteLine(employee.Name);
    }
}
```

This method works with `List<Employee>`, but it unnecessarily requires callers to provide a list. A caller may have an array, a queue, or another collection that can be enumerated.

If the method only needs iteration, express that requirement:

```csharp
public void PrintEmployees(IEnumerable<Employee> employees)
{
    foreach (Employee employee in employees)
    {
        Console.WriteLine(employee.Name);
    }
}
```

Now the method depends on the capability it needs—enumeration—rather than a specific implementation.

### Why this matters in real applications

- **Flexibility:** callers can pass different collection implementations.
- **Encapsulation:** APIs expose only the operations callers need.
- **Testability:** tests can supply different implementations more easily.
- **Maintainability:** an implementation can change without changing every method signature.
- **Intent:** an interface communicates whether a method needs iteration, mutation, indexing, or key-based lookup.

An interface is a contract. It does not, by itself, guarantee a particular internal data structure or performance characteristic.

## 2. `IEnumerable<T>`

### 2.1 What is `IEnumerable<T>`?

`IEnumerable<T>` represents a sequence that can be enumerated, typically using `foreach`.

```csharp
IEnumerable<string> names = new List<string>
{
    "Rahul",
    "Amit",
    "Priya"
};

foreach (string name in names)
{
    Console.WriteLine(name);
}
```

The interface provides the ability to obtain an enumerator. It does **not** promise that the sequence supports adding, removing, indexing, or even a cheap count operation.

### 2.2 Why does it exist?

Many data sources can be read one item at a time. A method that only reads items should not require a mutable collection.

Common examples:

- Printing or formatting items
- Validating a sequence
- Passing items into LINQ operations
- Processing results from a query
- Accepting data from arrays, lists, or iterator methods

### 2.3 What does it guarantee?

It guarantees that the object exposes enumeration through `GetEnumerator()`. Generic `IEnumerable<T>` is the standard interface used by `foreach` for strongly typed sequences.

It does **not** guarantee:

- An indexer such as `items[0]`
- An `Add()` or `Remove()` method
- A `Count` property
- That enumeration is repeatable or free of side effects
- That all items are already stored in memory

Some sequences are generated as they are enumerated. For example, iterator methods using `yield return` can produce items on demand.

### 2.4 Example: method requiring only enumeration

```csharp
static decimal CalculateTotal(IEnumerable<decimal> prices)
{
    decimal total = 0;

    foreach (decimal price in prices)
    {
        total += price;
    }

    return total;
}
```

The method can accept a `List<decimal>`, an array, or another enumerable sequence.

### 2.5 Common misconception: `IEnumerable<T>` means “a list”

It does not. It means the values can be enumerated. A list is one possible implementation; a query or generated sequence is another.

`IEnumerable<T>` itself does not promise a `Count` property. LINQ's `Count()` is an extension method, and depending on the source, it may need to enumerate the sequence.

## 3. `ICollection<T>`

### 3.1 What is `ICollection<T>`?

`ICollection<T>` extends `IEnumerable<T>` and adds a count and general collection operations.

| Member | Purpose |
|---|---|
| `Count` | Gets the number of elements |
| `Add(item)` | Adds an element |
| `Remove(item)` | Attempts to remove an element; returns `bool` |
| `Contains(item)` | Checks whether an element is present |
| `Clear()` | Removes all elements |
| `CopyTo(array, index)` | Copies elements into an array |
| `IsReadOnly` | Indicates whether mutation is supported through this interface |

### 3.2 Why does it exist?

Sometimes a method must do more than read items. It may need to check the number of items, add an item, remove an item, or test membership—without requiring list-specific indexing.

### 3.3 Example

```csharp
static void AddDefaultCategory(ICollection<string> categories)
{
    if (!categories.Contains("General"))
    {
        categories.Add("General");
    }
}
```

This method needs membership checking and adding. It does not need an indexer, so `ICollection<string>` expresses the requirement better than `IList<string>`.

### 3.4 Important behavior

```csharp
ICollection<string> names = new List<string> { "Amit", "Priya" };

bool removed = names.Remove("Amit");   // true
bool missing = names.Remove("Rahul"); // false
```

`Remove()` returning `false` means no matching element was removed. The absence of the element alone does not cause an exception.

`IsReadOnly` describes whether mutation is supported by that collection implementation through this interface. Do not assume every `ICollection<T>` is mutable.

### 3.5 What `ICollection<T>` does not provide

It does not provide an integer indexer. If a method needs `items[0]` or insertion at a specific position, it needs a more specific interface such as `IList<T>` or `IReadOnlyList<T>`.

## 4. `IList<T>`

### 4.1 What is `IList<T>`?

`IList<T>` extends `ICollection<T>` and adds operations for an ordered, index-based collection.

| Member | Purpose |
|---|---|
| `this[int index]` | Gets or sets an element at an index |
| `IndexOf(item)` | Finds the index of an item |
| `Insert(index, item)` | Inserts an item at a specified index |
| `RemoveAt(index)` | Removes the item at a specified index |

### 4.2 Why does it exist?

Some code needs to work with an ordered sequence where position matters—for example, changing an item at a particular position or inserting an item between two others.

### 4.3 Example: replacement versus insertion

```csharp
IList<string> names = new List<string> { "Amit", "Priya", "John" };

names[1] = "Meera";       // Replaces Priya
names.Insert(1, "Rahul"); // Inserts Rahul and shifts later items
```

After these operations, the list contains:

```text
Amit
Rahul
Meera
John
```

Assignment through the indexer replaces an existing element. `Insert()` creates a new position and shifts later elements in a list implementation such as `List<T>`.

### 4.4 Declared type controls accessible members

```csharp
List<int> concrete = new() { 3, 1, 2 };
IList<int> throughInterface = concrete;

concrete.Sort();              // Available on List<int>
throughInterface[0] = 10;     // Available on IList<int>
// throughInterface.Sort();   // Compile-time error
```

The object is still a `List<int>`, but the compiler exposes only the members available through the declared reference type. Use `List<T>` directly when its extra functionality is genuinely needed.

### 4.5 Common misconception

`IList<T>` does not mean every operation has the same performance for every implementation. The interface describes capabilities, not the internal data structure or complexity of every operation.

## 5. `IReadOnlyCollection<T>`

### 5.1 What is it?

`IReadOnlyCollection<T>` represents an enumerable collection with a `Count` property but without collection-mutation methods in its public interface.

```csharp
IReadOnlyCollection<string> names =
    new List<string> { "Amit", "Priya" };

Console.WriteLine(names.Count);

foreach (string name in names)
{
    Console.WriteLine(name);
}
```

### 5.2 Why does it exist?

It lets an API communicate: “You may enumerate these items and inspect the count, but this API does not offer collection mutation through this reference.” This is useful for returning results without advertising `Add`, `Remove`, or `Clear`.

### 5.3 Critical distinction: read-only interface is not immutability

```csharp
List<string> names = new() { "Amit", "Priya" };
IReadOnlyCollection<string> readOnlyView = names;

names.Add("Meera");

Console.WriteLine(readOnlyView.Count); // 3
```

The interface prevents mutation through `readOnlyView`, but the underlying list can still be changed through `names`. The read-only reference observes the same object.

`IReadOnlyCollection<T>` is a **read-only view of the available API**, not a guarantee that the underlying data can never change.

### 5.4 When to use it

Use it when callers need enumeration and count, but not positional access.

## 6. `IReadOnlyList<T>`

### 6.1 What is it?

`IReadOnlyList<T>` extends `IReadOnlyCollection<T>` and adds a getter-only indexer. It supports enumeration, `Count`, and reading an item by index, but it does not expose index assignment, `Add`, `Remove`, or `Insert`.

### 6.2 Example

```csharp
List<string> names = new() { "Rahul", "Amit" };
IReadOnlyList<string> readOnly = names;

Console.WriteLine(readOnly[0]); // Rahul
// readOnly[0] = "Priya";       // Compile-time error
// readOnly.Add("Priya");       // Compile-time error
```

### 6.3 Why does it exist?

A caller may need ordered data and positional reading, but should not be offered mutation methods through the API. For example, a service can return search results that consumers inspect by position.

### 6.4 Shared-reference behavior

```csharp
List<string> names = new() { "Rahul", "Amit" };
IReadOnlyList<string> readOnly = names;

names[0] = "Priya";

Console.WriteLine(readOnly[0]); // Priya
```

The read-only interface does not copy the list. Both references point to the same underlying object. If you need a stable snapshot, make a copy and expose that copy through an appropriate read-only API. A wrapper or interface alone does not guarantee a snapshot.

### 6.5 `IReadOnlyCollection<T>` vs. `IReadOnlyList<T>`

| Capability | `IReadOnlyCollection<T>` | `IReadOnlyList<T>` |
|---|---:|---:|
| Enumerate items | Yes | Yes |
| Read `Count` | Yes | Yes |
| Read by index | No | Yes |
| Mutate through interface | No | No |

## 7. `IDictionary<TKey, TValue>`

### 7.1 What is it?

`IDictionary<TKey, TValue>` represents key-value pairs. Each key must be unique according to the dictionary's key equality rules.

Typical uses include:

- Looking up a user by ID
- Mapping product codes to products
- Mapping configuration keys to values
- Counting occurrences of items

### 7.2 Important members

| Member | Purpose |
|---|---|
| `Keys` | Gets the keys |
| `Values` | Gets the values |
| `Count` | Gets the number of key-value pairs |
| `Add(key, value)` | Adds a pair; a duplicate key causes an exception |
| `Remove(key)` | Removes a pair by key |
| `ContainsKey(key)` | Checks whether a key exists |
| `TryGetValue(key, out value)` | Tries to retrieve a value without throwing for a missing key |
| `this[key]` | Gets or sets the value associated with a key |

### 7.3 `Add()` versus indexer assignment

```csharp
IDictionary<int, string> employees = new Dictionary<int, string>();

employees.Add(101, "Amit");
// employees.Add(101, "Priya"); // Throws ArgumentException: key already exists

employees[101] = "Priya"; // Replaces the existing value
employees[102] = "Meera"; // Adds a new key-value pair
```

Use `Add()` when duplicate keys should be treated as an error. Use indexer assignment when the intended behavior is to insert or replace.

Reading a missing key with `employees[999]` throws `KeyNotFoundException`.

### 7.4 Use `TryGetValue()` for expected misses

```csharp
if (employees.TryGetValue(101, out string? employeeName))
{
    Console.WriteLine(employeeName);
}
else
{
    Console.WriteLine("Employee not found");
}
```

The Boolean indicates whether the key was found. It does not simply tell you whether the returned value is non-null.

### 7.5 Common misconceptions

- Keys are unique; values do not have to be unique.
- A dictionary is not an index-based list.
- `Add()` and indexer assignment do not have the same duplicate-key behavior.
- `TryGetValue()` is often preferable when a missing key is an expected outcome.
- The key does not have to be an employee ID; it can be any suitable key type.

## 8. Comparison of collection interfaces

| Interface | Main capability | Mutation exposed? | Indexing |
|---|---|---:|---|
| `IEnumerable<T>` | Enumeration | No | No |
| `ICollection<T>` | Enumeration, count, general collection operations | Yes, when supported | No |
| `IList<T>` | Collection operations plus positional operations | Yes, when supported | Yes |
| `IReadOnlyCollection<T>` | Enumeration and count | No | No |
| `IReadOnlyList<T>` | Enumeration, count, positional reading | No | Read-only |
| `IDictionary<TKey, TValue>` | Key-value lookup and dictionary operations | Yes, when supported | Key-based indexer |

### Choosing the least powerful interface

- Only loop through values: `IEnumerable<T>`
- Need count and general add/remove/membership operations: `ICollection<T>`
- Need positional insertion, replacement, or removal: `IList<T>`
- Return enumerable data and count without exposing mutation: `IReadOnlyCollection<T>`
- Return ordered data with index-based reading: `IReadOnlyList<T>`
- Find values by unique keys: `IDictionary<TKey, TValue>`

Choose based on required capabilities, not just habit. Interfaces communicate available operations; they do not automatically make objects immutable or thread-safe.

## 9. Understanding questions with answers

### Q1. Why use `IEnumerable<T>` instead of `List<T>` as a parameter?

Because the method may only need to enumerate values. `IEnumerable<T>` allows more implementations and avoids requiring list-specific behavior.

### Q2. Does `IEnumerable<T>` guarantee a `Count` property?

No. LINQ's `Count()` extension method is separate from a `Count` property and may need to enumerate the sequence.

### Q3. What does `ICollection<T>` add to `IEnumerable<T>`?

It adds `Count` and general collection operations such as `Add`, `Remove`, `Contains`, and `Clear`, where supported.

### Q4. What does `IList<T>` add?

An indexer and positional methods such as `IndexOf`, `Insert`, and `RemoveAt`.

### Q5. Does `IReadOnlyList<T>` mean nobody can change the underlying list?

No. It prevents mutation through that interface reference, but another reference may still mutate the same object.

### Q6. What is the difference between `IReadOnlyCollection<T>` and `IReadOnlyList<T>`?

Both support enumeration and `Count`; `IReadOnlyList<T>` additionally supports reading by index.

### Q7. What happens if `IDictionary<TKey, TValue>.Add()` receives an existing key?

It throws an `ArgumentException` because dictionary keys must be unique.

### Q8. What is the difference between `TryGetValue()` returning `false` and returning `true`?

`false` means the key was not found. `true` means the key was found and its value was assigned to the `out` variable.

### Q9. If a variable is declared as `IList<int>` but refers to a `List<int>`, can it call `Sort()`?

Not through that interface reference, because `Sort()` is not a member of `IList<T>`. The runtime object remains a `List<int>`, but compile-time member access follows the declared reference type.

### Q10. Does an interface guarantee performance or thread safety?

No. An interface primarily defines a contract of available members. Performance and thread-safety guarantees depend on the specific implementation and its documentation.

## 12. Final revision summary

- **`IEnumerable<T>`:** enumerate values.
- **`ICollection<T>`:** enumerate, count, and perform general collection operations.
- **`IList<T>`:** collection operations plus positional access and modification.
- **`IReadOnlyCollection<T>`:** enumerate and count without exposing mutation methods.
- **`IReadOnlyList<T>`:** read-only interface with index-based reading.
- **`IDictionary<TKey, TValue>`:** access values through unique keys.

The most important design principle is: **declare the capability your code needs, not a more specific collection than necessary.** A read-only interface limits the operations available through a reference; it does not automatically make the underlying object immutable.
